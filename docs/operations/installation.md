# Installing ITRMS (the production profile)

The operator's runbook for one installation (one region, ADR-0008), on one machine. The production profile is
`infra/compose/production.yml` over `infra/compose/docker-compose.yml`; `tools/prod-stack.mjs` runs its steps and CI runs the
same steps on every change (the *production profile* job, task 0.26a), with the backups and the restore drill: the
database's (task 0.26b1, §7) and the files' (task 0.26b2, §8).

## 1. The machine
- **Linux** with Docker Engine and the Compose plugin (not Docker Desktop: ADR-0008), in Ethiopia (PDP Proclamation 1321/2024).
- **The data disk encrypted with LUKS**, mounted where Docker keeps its volumes (or bind it there): PostgreSQL, the object store
  and Keycloak hold personal data at rest. Unlock it at boot with a key kept off the machine.
- **The clock** kept by **chrony** on the host (`chrony` package, two or more NTP sources): signed tokens, audit times and the QR
  codes' validity depend on it. The containers take the host's clock.
- **The three hostnames** (architecture §12): `app.<domain>` (the staff app, and Keycloak's sign-in pages under `/auth`) and
  `verify.<domain>` to the machine in DNS; only `verify` is public by design, `app` is limited to the offices' networks or a VPN
  where they have one. The third, Keycloak's administration, has no public name: it answers on the machine's loopback
  (`http://127.0.0.1:18080/auth`), reached over SSH.
- **Firewall**: 80 and 443 in, SSH for the operator. Nothing else listens outside the machine.

## 2. The certificates
In `infra/compose/tls/`: `app.fullchain.pem`, `app.key.pem`, `verify.fullchain.pem`, `verify.key.pem` (the bureau's CA or
ACME), and `ca.pem`, a CA the processes trust beside the system's (the bureau's own; for a public CA, any certificate the chain
ends in). A test installation gets a self-signed set from `tools/prod-stack.mjs` when the folder is empty.

## 3. The settings
`infra/compose/.env.production`, generated by `node tools/prod-stack.mjs up` on first start: the database roles' passwords,
Keycloak's, the session and field-encryption keys, the object store's. Owner-only, never committed; keep a copy in the bureau's
safe (sops + age, tech-stack). Set before the first start:

| Variable | Meaning |
|---|---|
| `ITRMS_DOMAIN` | the installation's domain (`app.` and `verify.` are under it) |
| `ITRMS_VERSION` | the released images' version (a tag, e.g. `v0.1.0`); unset builds them from the checkout (`local`) |
| `ITRMS_REGISTRY` | where the images are pulled from (default `ghcr.io/wwwabebayehualaro-ai`); offline: `docker load` a tarball |
| `ITRMS_EGRESS_ALLOW` | the hosts the API may call out to (the national platform, an SMS gateway), comma-separated; empty: none |

## 4. First start
```bash
node tools/prod-stack.mjs up            # an empty installation: the schema, the realm, nothing else
node tools/prod-stack.mjs up --demo     # a demo installation: also the demo's data (docs/demo-plan.md)
node tools/prod-stack.mjs smoke         # the checks: TLS on both hostnames, the verifier, sign-in, the blocked admin
```
Then the bureau's own data: its org tree, catalogue and users with the setup container (`docker compose … --profile setup run
--rm setup node dist/seed.cjs org <file>`; the seed command's usage lists the rest), and its administrators in Keycloak.

## 5. Upgrades
Backup → `migrate` → restart (ADR-0008): set `ITRMS_VERSION` to the new release, `docker compose … pull`, take a backup,
`docker compose … --profile setup run --rm migrate`, then `docker compose … up -d`, then `docker compose … restart edge s3`
(Nginx and the gates look the processes' addresses up when they start). Rollback is the previous version, and a
restore if a migration was not backwards-compatible (migrations follow expand/contract to avoid that).

## 6. What runs
| Service | Image | Role |
|---|---|---|
| `edge` | `itrms-edge` | Nginx: TLS, the exposure rules (`infra/compose/nginx`), the verifier's static pages |
| `web` | `itrms-web` | the staff app and its BFF |
| `api`, `worker` | `itrms-api` | the API; the outbox, jobs and identity sync |
| `worker-documents` | `itrms-documents` | the PDF worker (Chromium) |
| `migrate`, `setup` | `itrms-api` | one-shot: the migrations; the seeds (profile `setup`) |
| `egress` | `itrms-egress` | the only route out, to `ITRMS_EGRESS_ALLOW` |
| `s3`, `admin` | `itrms-gate` | one port each between networks: the object store's S3 port; Keycloak's on the loopback |
| `postgres` | `itrms-postgres` | PostgreSQL 16 (the pinned upstream image) with pgBackRest: archives every WAL segment |
| `backup` | `itrms-backup` | the pgBackRest repository host: pulls the backups, keeps the encrypted repository (§7) |
| `drill` | `itrms-postgres` | the restore drill's scratch database (profile `drill`; removed after each drill) |
| `replica` | pinned SeaweedFS image | a second store, kept a copy of the bucket (§8) |
| `files-sync` | `itrms-files-backup` | keeps that copy: every change to the bucket, into the second store (§8) |
| `files-backup` | `itrms-files-backup` | the bucket mirrored as files, a restic snapshot of them every night (§8) |
| `restic` | `itrms-restic` | restic's rest-server, append-only: the files' backup repository (§8) |
| `valkey-*`, `keycloak`, `seaweedfs` | pinned upstream images | the queues, sign-in, the files |

The processes, the databases and Keycloak are on an internal network with no route out; `edge` alone takes connections, and
`egress` alone makes them (the smoke check tries both ways from the API). The object store is alone on a second internal
network: its master, volume and filer ports have no authentication, so the processes reach its S3 port only, through `s3`.
The API believes `X-Forwarded-For` from the internal network's subnet (`ITRMS_SUBNET`) only. The PDF worker's memory is capped
(`ITRMS_DOCUMENTS_MEMORY`, 1 GB): Chromium's memory is not Node's.

## 7. Backups and the restore drill (the database)
pgBackRest (ADR-0012, ADR-0031 item 13), in **pull mode**: the repository host (`backup`) takes the backups from the database
and keeps them; the database only archives its WAL to it. The application machine does not hold the repository, the
repository host's key or (on site) the repository's encryption key. It is not a protection against a broken-into application
machine: pgBackRest has no archive-only permission, so the database's certificate can write to and remove from its stanza.
That protection is the off-site, append-only copy (task 0.26d).

- **Where:** on site, `backup` runs on a **second machine** in the bureau (its own disk, LUKS too); the profile runs it as a
  container beside the others so that one machine shows it whole. Off-site copies inside Ethiopia are task 0.26d.
- **Mutual TLS:** each side has a certificate from the backups' own CA, `infra/compose/backup-tls/` (`ca.pem`; `postgres.*`,
  `backup.*`, `drill.*`), made by `tools/prod-stack.mjs` when the folder is empty; the CA's key is deleted once they are
  signed. Each container mounts `ca.pem` and its own pair only. The database accepts only `backup`; the repository host only
  `postgres` and `drill`. On site the database machine keeps `ca.pem` and `postgres.*`, the backup machine `ca.pem`,
  `backup.*` and `drill.*`. They are valid 825 days: renew them (empty the folder, run `up`, restart `postgres` and
  `backup`) before then.
- **Encrypted:** the repository is AES-256 with `PGBACKREST_CIPHER_PASS`. Only the repository host needs it: on site it is in
  the backup machine's settings, not the application machine's. **Without that key the backups cannot be read**: keep its copy
  in the bureau's safe.
- **The schedule** (Addis Ababa time, on the repository host): a full backup on Sunday at 01:00, a differential the other nights,
  the WAL continuously (a segment at least every 5 minutes, `archive_timeout`). Retention: 30 days back, to any moment in them.
  ADR-0012's 12 monthly copies are kept off-site (task 0.26d). The archive command is set by `up` (`ALTER SYSTEM`) once the
  stanza exists, so the database's first start never waits on the repository host.

```bash
node tools/prod-stack.mjs backup --type full   # a backup now, and a snapshot of the files (§8); before an upgrade (§5)
node tools/prod-stack.mjs drill                # the restore drill, by hand
```
**The drill** takes one snapshot of the live database and, in the same statement, a restore point. It restores the latest
backup into the scratch database `drill`, recovers it to that point, and compares the two: the row count of every table, the
audit log's rows with a digest over them in order, and the row count of every table of Keycloak's database (the users and their
second factors, in the same backup; its snapshot is a moment earlier, so a sign-in in between fails the drill, which is then run
again). It checks the files too (§8). It fails on any difference and on an empty restore, and writes its report (counts and digests, no personal data) to
`infra/compose/drill-reports/`. The scratch database and its volume are removed afterwards, also when it fails: they are a copy
of the personal data.

**Monthly, automated** (ADR-0012): `infra/backup/itrms-drill.service` and `itrms-drill.timer` run it on the first Sunday of every
month at 03:00, after the night's backup. Install them with the checkout in `/opt/itrms`: copy both to `/etc/systemd/system/`,
then `systemctl enable --now itrms-drill.timer`. A failed drill fails the unit (`systemctl status itrms-drill`, the journal), and
the next one is an incident until it passes. CI runs the drill on every change after a full and a differential backup and a write
only the archived WAL holds (`drill --probe`).

**A real restore** (the database lost), with the repository host running:
1. Stop what uses the database: `docker compose … stop api worker worker-documents web keycloak edge`.
2. Remove the database's container and its volume (Docker keeps a volume a container still has):
   `docker compose … rm -s -f postgres`, then `docker volume rm itrms_postgres-data`.
3. Restore into a new volume: `docker compose … run --rm --no-deps --entrypoint "itrms-pgbackrest restore" postgres
   --type=default` (the arguments are pgBackRest's restore options: `--type=time "--target=<time>"` for a moment before a
   mistake; it refuses a volume that is not empty).
4. Start `postgres`, take a full backup (`backup --type full`), then `docker compose … up -d`, then `restart edge s3` (§5).

## 8. Backups and the restore drill (the files)
ADR-0031 item 13: the files are copied two ways, each on the backup machine on site (here, containers beside the others).

- **A second store** (`replica`), kept a copy of the bucket by `files-sync` within seconds of every change, one way (the
  second store never writes back), deletions included: `weed filer.backup` following the bucket's changes with the second
  store's filer as its sink. (ADR-0031 names `weed filer.sync`; in this layout it received no change, so the same follower
  that makes the mirror makes the copy.) It is what a lost disk is restored from fastest: the processes can be pointed at it.
- **Snapshots, append-only:** `files-backup` mirrors the bucket as plain files (`weed filer.backup`, as they change,
  deletions included: a purged file leaves the mirror, and the snapshots' retention ages it out) and takes
  a restic snapshot of the mirror every night at 01:30 to `restic`, restic's rest-server run `--append-only`: a client can
  add a snapshot but never remove or rewrite one, so a broken-into application machine cannot destroy the history. The retention
  (ADR-0012: 30 daily, 12 monthly) runs on the rest-server's own side every night at 04:00.
- **Secrets:** the repository is encrypted with `RESTIC_PASSWORD`, and the rest-server takes `RESTIC_SERVER_PASSWORD` (one
  user, its own repository, `--private-repos`), both from `.env.production`; on site they are on the backup machine. **Without
  `RESTIC_PASSWORD` the snapshots cannot be read**: keep its copy in the bureau's safe. The rest-server's TLS certificate is
  `restic.*` from the backups' CA (§7).
- **What is not in them:** a file still being uploaded or checked (`pending`, `checking`) and a rejected one: the drill counts
  only `stored` files.

**The drill** (§7, the same command) checks the files as well: every `stored` file the live database names is in the second
store and the mirror, with its size and SHA-256 (they are given ten minutes to follow a new upload); then a snapshot is taken,
the latest snapshot is restored into a scratch folder, and every `stored` file the *restored* database names is in it with its
size and SHA-256. The scratch folder is removed after the listing.

**A real restore** (the store lost): stop the processes, then either point them at the second store, or restore the latest
snapshot into a new store: `docker compose … run --rm --entrypoint sh files-backup -c 'restic restore latest --host itrms
--target /restore'` with a volume at `/restore`, and upload its `mirror/` folder to the bucket at the same keys (`weed
filer.copy` or any S3 client). Then run the drill.
